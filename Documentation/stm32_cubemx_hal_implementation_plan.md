# STM32CubeMX / HAL Implementation Plan
Target: **STM32F411CEU6**  
Project goal: implement the iBooster interceptor firmware described in `stm32_firmware_spec.md`

### 1.1 Recommended tools
- **STM32CubeMX** or **STM32CubeIDE**
- STM32 HAL package for **STM32F4**
- optional editor: VS Code

### 1.2 Project language

### 1.3 MCU selection

## 2. CubeMX Pin Configuration

## 2.1 GPIO pins
Configure these pins:

- **PB1** → `GPIO_EXTI1` → `S2_IN`
- **PB0** → `GPIO_EXTI0` → `S4_IN`
- **PA7** → `TIM3_CH2` → `S2_OUT`
- **PA6** → `TIM3_CH1` → `S4_OUT`
- **PB10** → `GPIO_Output` → relay control
- **PA5** → `GPIO_Output` → level shifter enable

### 2.2 GPIO defaults
At init:
- `PB10` relay = **reset/off**
- `PA5` level shifter enable = **reset/off**

### 2.3 EXTI edge selection
For both PB0 and PB1:
- trigger on **rising and falling edge**

## 3. Timer Configuration

## 3.1 TIM3 — output PWM
Purpose:
- generate modified PWM outputs on PA6/PA7

### TIM3 channels
- CH1 = PA6 = S4 output
- CH2 = PA7 = S2 output

### TIM3 target behavior
- output frequency: **1 kHz**
- preload enabled on both PWM channels
- duty updated by writing CCR1/CCR2

### Suggested configuration
Choose timer clock and prescaler so the timer counter runs at **1 MHz**.

Example:
- timer tick = 1 µs
- `ARR = 999`
- PWM frequency = 1000 Hz

Then:
- `CCR = duty_percent * 10`
- e.g. 17% → 170
- e.g. 83% → 830

### CubeMX setup
- enable TIM3
- set Channel 1 = PWM Generation CH1
- set Channel 2 = PWM Generation CH2
- prescaler for 1 MHz timer base
- counter period = 999
- enable preload if available in generated config or add manually in user code

---

## 3.2 TIM2 — free-running timestamp timer
Purpose:
- hardware timestamp source for EXTI edge measurement

### TIM2 target behavior
- free-running up-counter
- 1 MHz count frequency
- maximum period / large ARR

### Suggested configuration
- prescaler set for **1 MHz**
- period set to **0xFFFFFFFF**
- no output channels needed
- start base timer in normal mode

### CubeMX setup
- enable TIM2 as internal clock
- no interrupts required
- no channels required
- configure prescaler
- ARR = max

---

## 3.3 TIM10 — 1 kHz control loop
Purpose:
- deterministic control-loop tick

### TIM10 target behavior
- update interrupt at **1 kHz**

### Suggested configuration
- timer clock reduced to 10 kHz or 100 kHz, whatever is convenient
- set period for 1 ms update event

Example:
- if counter clock = 10 kHz
- `ARR = 9`
- interrupt every 1 ms

### CubeMX setup
- enable TIM10 base timer
- enable update interrupt
- configure NVIC for TIM1_UP_TIM10 interrupt

### Acceptable fallback
If TIM10 is awkward in the chosen project:
- use SysTick at 1 kHz for control loop
- but keep HAL timebase implications in mind

---

## 4. NVIC / Interrupt Setup

Enable:
- **EXTI0_IRQn** for PB0
- **EXTI1_IRQn** for PB1
- **TIM1_UP_TIM10_IRQn** for control loop if using TIM10

Priority guidance:
- EXTI0 / EXTI1: higher priority than control loop
- TIM10: lower than EXTI
- keep priorities simple and documented

Suggested:
- EXTI priority = 1
- control loop priority = 2

Do not make serial interrupts timing-critical.

---

## 5. Clock Configuration

Goal:
- stable system clock high enough for comfortable ISR latency margin

Recommended:
- normal STM32F411 performance clock setup as generated by CubeMX
- no special overclocking or exotic clock tree needed

Requirement:
- know the actual timer clocks so 1 MHz prescalers are calculated correctly

Important:
- verify APB timer clock multiplication rules in STM32F4
- do not assume timer clock equals APB clock without checking

## 6. Generated HAL Initialization Calls

In `main.c`, CubeMX will typically generate:
- `HAL_Init()`
- `SystemClock_Config()`
- `MX_GPIO_Init()`
- `MX_TIM2_Init()`
- `MX_TIM3_Init()`
- `MX_TIM10_Init()` if used
- `MX_USARTx_UART_Init()` if serial UART is used

After those, user code must start peripherals explicitly.

---

## 7. Peripheral Start Order in User Code

After CubeMX init functions:

1. force relay off
2. force level shifter off
3. start TIM3 PWM on CH1 and CH2
4. load safe/rest CCR values
5. start TIM2 base counter
6. start TIM10 base interrupt
7. enable level shifter
8. begin startup validation logic in control loop

### Required HAL start calls
- `HAL_TIM_PWM_Start(&htim3, TIM_CHANNEL_1);`
- `HAL_TIM_PWM_Start(&htim3, TIM_CHANNEL_2);`
- `HAL_TIM_Base_Start(&htim2);`
- `HAL_TIM_Base_Start_IT(&htim10);` if TIM10 is used

## 8. CubeMX Code Generation Strategy

### 8.1 Use user-code sections only
All custom code should live in:
- `/* USER CODE BEGIN ... */`
- `/* USER CODE END ... */`

This avoids loss during re-generation.

### 8.2 Keep hardware config in CubeMX
Use CubeMX for:
- clocks
- pin mux
- timer base setup
- NVIC enabling

Use user code for:
- runtime logic
- control/state machine
- EXTI measurement logic
- PWM duty updates
- serial CLI
- safety logic

## 10.2 `output_pwm.c`
Responsibilities:
- convert duty % to TIM3 compare values
- expose `output_pwm_set_duty(float s2, float s4)`
- expose `output_pwm_init_safe_state()`

Implementation notes:
- use ARR value from TIM3 config
- clamp outputs to 0–100%
- write:
  - `__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_1, s4_ccr);`
  - `__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_2, s2_ccr);`

Recommended startup:
- initialize CH1/CH2 to rest values before relay can energize

---

## 10.3 `input_capture.c`
Responsibilities:
- own raw measurement structs
- process edge events from EXTI callbacks
- read TIM2 counter as timestamp
- expose read/copy API for control loop

### HAL integration point
Use:
- `HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)`

Inside callback:
- if `GPIO_Pin == GPIO_PIN_0`, handle S4 edge
- if `GPIO_Pin == GPIO_PIN_1`, handle S2 edge

Timestamp source:
- `uint32_t now = __HAL_TIM_GET_COUNTER(&htim2);`

Edge polarity:
- read GPIO state using `HAL_GPIO_ReadPin(...)`
- or direct register read later if optimization needed

Per-channel logic:
- rising edge: compute period from previous rise
- falling edge: compute high time from last rise
- update `last_edge_us`

No float math here.

## 11. Main Control Tick Integration

### 11.1 HAL callback
If using TIM10:
- implement `HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)`

Pseudo-flow:
- if `htim->Instance == TIM10`
  - run 1 kHz control tick function

### 11.2 Tick work
Inside the control tick:
1. copy raw input capture data
2. determine validity/staleness
3. compute duty values
4. apply EMA
5. compute travel
6. update startup qualification
7. check plausibility fault
8. update mode/state
9. decide relay state
10. decide output PWM
11. write TIM3 CCRs

Keep this bounded and deterministic.

---

## 12. EXTI Measurement Details

### 12.1 Measurement rules
For each channel:
- `period_us = rise_now - previous_rise`
- `high_us = fall_now - last_rise`

### 12.2 Validation rules
Only accept updates if:
- period within configured range
- high time > 0
- high time < period

### 12.3 Wrap handling
Because TIM2 is 32-bit and running at 1 MHz:
- wrap is infrequent
- unsigned subtraction handles wrap safely

Example:
- `delta = now - then;`

No special wrap code needed if all timestamps are `uint32_t`.

---

## 13. PWM Output Details

### 13.1 TIM3 frequency
Keep output PWM at **1 kHz** unless testing shows iBooster requires slightly different frequency matching.

### 13.2 Compare update strategy
Use CCR preload / timer update semantics so changes apply cleanly at the next cycle boundary.

If CubeMX does not fully enable desired preload behavior, set it in user code after timer init.

### 13.3 Mapping
- TIM3 CH1 / PA6 = S4 output
- TIM3 CH2 / PA7 = S2 output

This preserves intuitive channel pairing.

---

## 14. Startup Logic Implementation

State machine in software should do:

### `BOOT`
- hardware initialized
- relay off
- level shifter off
- outputs set to safe values

### `WAIT_FOR_VALID_INPUT`
- level shifter on
- monitor captures
- require valid data for at least 50 ms
- require no plausibility fault
- require rest pedal before allowing transition to active routing

### `PASSTHROUGH_READY`
- relay still off
- normal passthrough state
- active path permitted when mode logic requests it

### `ACTIVE`
- relay on
- outputs driven from lookup curve

### `COMMAND`
- relay on
- outputs driven from command target/ramp

### `FAULT_LATCHED`
- relay off
- stay latched until reset

## 18. Bring-Up Sequence

Recommended validation order:

### Phase 1: clocks and GPIO
- confirm MCU boots
- confirm relay pin defaults off
- confirm level shifter defaults off

### Phase 2: TIM2 timestamp timer
- verify free-running 1 MHz count on debugger/watch window

### Phase 3: TIM3 output PWM
- verify PA6/PA7 produce stable 1 kHz PWM
- verify CCR changes alter duty correctly

### Phase 4: EXTI edge capture
- confirm PB0/PB1 interrupts fire
- confirm raw period/high time update correctly with bench signal

### Phase 5: control loop
- verify 1 kHz periodic callback
- verify filtered duty/travel computation

### Phase 6: startup and relay logic
- verify 50 ms valid window
- verify relay never energizes during invalid input
- verify relay only energizes at rest

### Phase 7: fault logic
- inject plausibility mismatch
- verify latch to passthrough

## 19. CubeMX Pitfalls to Watch For

1. **Timer clock assumptions**
   - verify actual timer clock, do not assume
2. **GPIO pull settings**
   - keep input pulls aligned with board design
3. **EXTI both-edge config**
   - verify both edges are actually enabled
4. **TIM3 preload behavior**
   - verify CCR updates are glitch-free on scope
5. **Code regeneration**
   - keep custom code inside user sections
6. **Interrupt priority confusion**
   - document final priority assignments

## 20. Deliverable Checklist

A CubeMX-generated project is ready for firmware implementation when it has:

- MCU set to STM32F411CEUx
- PB0/PB1 configured as EXTI inputs
- PA6/PA7 configured as TIM3 PWM outputs
- PB10/PA5 configured as GPIO outputs
- TIM2 configured as free-running 1 MHz timer
- TIM3 configured as 1 kHz dual-channel PWM
- TIM10 configured as 1 kHz periodic interrupt, or SysTick chosen instead
- NVIC enabled for EXTI and control timer
- UART configured if using serial CLI immediately
